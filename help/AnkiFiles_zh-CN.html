1. 这份说明书解决什么问题

Anki 的媒体文件在 iPhone 上的操作，和桌面、Android 完全不同。桌面和 Android 可以直接打开文件管理器操作媒体目录，iPhone 不行——iOS 的沙盒机制让 AnkiMobile 的媒体库对用户完全封闭。

这导致几个现实问题：

  1. 怎么把几十 G 的媒体传进 iPhone？ 走 AnkiWeb 同步不可能，只能通过 apkg 离线打包，再借助 iTunes 文件共享或网盘传输。
  2. Windows 上视频怎么播放？ Windows 版 Anki 只支持 WebM，不支持 MP4。所以同一个视频要准备两份，给 iPhone 用 MP4，给 Windows 用 WebM。
  3. 怎么让媒体在 iPhone 上精准定位？ 不是所有视频格式都支持 seek。不满足条件的文件在 iPhone 上播放正常但进度条乱跳。
  4. 怎么删除已经导入的媒体？ Anki 的"检查媒体"可以清理未使用的媒体，但前提是文件中已经不再有 [sound:] 引用，而且文件小于 100MB。
  5. 为什么导入 apkg 总是失败？ 因为 iPhone 上已存在同名 deck，AnkiMobile 不会自动覆盖，必须先删除旧 deck 再导入。

这份说明书针对这几个问题，给出完整的、可操作的流程。

2. 三个平台的本质区别

2.1 对比表

平台媒体文件访问方式视频格式是否需要媒体包
Windows直接打开 collection.media 文件夹，增删改都行仅 WebM不需要
macOS直接打开 collection.media 文件夹，增删改都行MP4 / WebM 均可不需要
Android直接访问 AnkiDroid 的媒体目录，增删改都行MP4不需要
iPhone / iPad沙盒封闭，无法直接访问文件系统MP4必须

2.2 桌面与 Android 的常规做法

  • 直接把媒体文件拷进 collection.media 文件夹
  • 卡片里的 [sound:] 引用自动找到文件
  • 删除就是直接从文件夹删
  • 覆盖就是直接替换文件
  • 检查媒体能正常工作

2.3 iPhone 的困境

本说明书主要面向 iPhone / iPad。桌面和 Android 用户可以直接操作媒体文件夹，只需要注意 Windows 的 WebM 格式限制。

iPhone 的沙盒机制意味着：

  • 无法访问文件系统 → 没法手动拷贝、删除、替换
  • 唯一的文件传输通道是 apkg → 媒体必须被打包才能进手机
  • [sound:] 是让 Anki 把文件装进 apkg 的唯一手段
  • 删除媒体要依赖 Anki 的"检查媒体"，通过删除 [sound:] 引用触发
  • 导入 apkg 前必须先删除同名 deck，否则导入会被跳过

3. Windows 视频格式限制

Windows 版 Anki 只支持 WebM 视频，不支持 MP4。这是 Windows 版 Anki 的播放引擎限制，和 iPhone 无关。

3.1 为什么会有这个限制

Anki 在 Windows 上用的是 QtWebEngine（基于 Chromium），Chromium 在 Windows 上默认不带 H.264 解码器（因为专利授权问题），所以 MP4 播不了。WebM 用的是 VP8/VP9 编码，开源免费，所以被支持。

3.2 对工作流的影响

同一个视频，需要在两个平台上有两份：

平台视频格式编码
iPhone / iPad / Android / macOSMP4H.264 + AAC
WindowsWebMVP8/VP9 + Vorbis/Opus

3.3 媒体包 deck 的分工

这就是为什么媒体包要按格式分组。以 Seinfeld 为例：

0. Resources/
├── MP4 Seinfeld/     （给 iPhone / Android / macOS 用）
│   ├── Seinfeld S01 Mp4
│   ├── Seinfeld S02 Mp4
│   └── ...
└── WEBM Seinfeld/    （给 Windows 用）
    ├── Seinfeld S01 Webm
    ├── Seinfeld S02 Webm
    └── ...

两个 deck 是独立准备的，各自导出 apkg，各自传输到对应平台。

3.4 音频不受此限制

音频格式在 Windows 上限制较少，MP3、M4A 都能播。所以 MP3 系列只需要一份。

4. 核心机制：[sound:] 的作用

4.1 常见的误解

很多人以为 [sound:] 是用来控制播放的。在媒体传输场景里，它的真正作用是：

让 Anki 在导出 apkg 时，把对应的媒体文件打包进去。

4.2 为什么必须用它

Anki 导出 apkg 时，会扫描卡片里所有 [sound:] 和 <img> 引用，把这些引用指向的媒体文件收集起来打包。没有引用的文件，Anki 根本不知道它们属于这个牌组，就不会打包。

对于几十 G 的媒体，这尤其关键：

  • AnkiWeb 同步不可能（流量、100MB 单文件限制）
  • apkg 是唯一可靠的批量离线传输方式
  • 而 apkg 只能通过 [sound:] 声明媒体

4.3 [sound:] 的三重角色

角色说明
传输声明告诉 Anki 这些文件要打进 apkg
清理开关从卡片里删掉 [sound:] 引用，重新导入后，对应媒体变成"未使用"，可被"检查媒体"删除
覆盖触发同名文件覆盖时，Anki 只识别 [sound:] 引用的文件是否更新

4.4 [sound:] 不负责播放控制

真正的播放控制由卡片模板的 JavaScript 完成（见 VlsPlayer Series / Notes 说明书）。[sound:] 在这里只是一个"文件清单"。

5. 媒体包 deck 的结构

5.1 设计原则

  • 每个系列一个 deck：便于单独导出、单独传输、单独清理
  • 每季一张卡片：有季编号的系列，每季单独一张卡片
  • 无季编号的系列，整个系列一张卡片
  • 按格式分组：MP3 / MP4 / WEBM 分开，便于按平台选用
  • deck 名和字段用纯英文：避免路径的 Unicode 问题

5.2 推荐结构（有季编号）

以 Seinfeld 为例：

0. Resources/
├── MP4 Seinfeld/
│   ├── Seinfeld S01 Mp4   （卡片 1，sound 字段列 S01 的所有集）
│   ├── Seinfeld S02 Mp4   （卡片 2，sound 字段列 S02 的所有集）
│   ├── Seinfeld S03 Mp4
│   ├── ...
│   └── Seinfeld S09 Mp4
└── WEBM Seinfeld/
    ├── Seinfeld S01 Webm
    └── ...

5.3 推荐结构（无季编号）

以 Atomic Habits 为例：

0. Resources/
├── MP3 Atomic Habits      （一个 deck，一张卡片）
├── MP3 CWE                （一个 deck，一张卡片）
├── MP4 DDM
└── MP4 Friends

5.4 卡片字段结构

每张笔记有两个字段：

字段名内容
Front一行纯文字，如 Seinfeld S02 Mp4，用作标识符
sound一行一个 [sound:xxx]，列出这张卡片对应的所有媒体

5.5 sound 字段示例

有季编号的（Seinfeld S02）：

[sound:sf_s02e01.mp4]
[sound:sf_s02e02.mp4]
[sound:sf_s02e03.mp4]
...
[sound:sf_s02e12.mp4]

无季编号的（CWE）：

[sound:cwe_01.mp4]
[sound:cwe_02.mp4]
[sound:cwe_03.mp4]
...
每个 [sound:] 占一行，便于阅读和手动增删。不要写成一行连续串，那样以后不好维护。

5.6 为什么每季一张卡片

优点说明
体积可控一季的 apkg 不会太大，传输更稳
独立更新更新某一季时，只重新导那一张卡片
独立清理清理时按季清理，粒度清晰
命名清晰Front 字段一眼看出是哪一季

6. 文件命名规范

6.1 两种命名格式

根据内容是否有季编号，命名分两种：

无季编号

前缀_集号.扩展名

示例：

cwe_01.mp4
cwe_02.mp4
atomic_habits_00.mp3
atomic_habits_01.mp3

有季编号

前缀_s季号e集号.扩展名

示例：

sf_s02e01.mp4
sf_s02e02.mp4
sf_s02e12.mp4

6.2 规则

项目规则
前缀系列缩写，2-4 字母小写，如 sf、cwe、ah
分隔符下划线 _
季号s + 两位补零，如 s01、s02（仅在有季编号时使用）
集号e + 两位补零，如 e01、e12（仅在有季编号时使用）
集号（无季）两位或三位补零，如 01、001
扩展名统一，同一系列内不混用
禁止中文、空格、大写、特殊字符

6.3 序号位数怎么定

  • 少于 100 集 → 两位（01 ~ 99）
  • 多于 100 集 → 三位（001 ~ 999）
  • 位数必须统一，否则排序会乱：_9.mp4 会排在 _10.mp4 后面

6.4 同一系列多种格式

sf_s02e01.mp4   （iPhone / Android / macOS）
sf_s02e01.webm  （Windows 专用）
sf_s02e01.mp3   （音频）

文件名相同，扩展名不同。这样卡片里的引用结构一致，按平台替换扩展名即可。

6.5 和 VlsPlayer Series 卡片的一致性

这个命名规范必须和 Series 卡 Timeline 字段的拼接规则一致。Series 卡代码里的拼接逻辑是：

文件名 = 前缀 + "_" + (季号为空 ? 集号 : "s" + 季号 + "e" + 集号) + 扩展名
  • 季号为空 → cwe_01.mp4
  • 季号非空 → sf_s02e01.mp4
媒体包 deck 里的 [sound:] 引用、Series 卡 Timeline 字段、实际文件名，三者必须完全一致，否则卡片找不到文件。

6.6 批量生成 [sound:] 引用

有季编号（Bash，假设一季 12 集）：

for i in $(seq -w 1 12); do echo "[sound:sf_s02e${i}.mp4]"; done

无季编号：

for i in $(seq -w 1 30); do echo "[sound:cwe_${i}.mp4]"; done

输出直接贴进 sound 字段。

7. 用 ffmpeg 压缩与转换

7.1 为什么必须压缩

  • 原始视频动辄几十 G，iPhone 装不下
  • Anki 对单文件有 100MB 的处理限制
  • AnkiMobile 加载大文件会卡顿
  • 语言学习只需要看清字幕和口型，画面细节不重要

7.2 视频压缩：只需指定高度

转视频时不需要指定宽度，用 -2 让 ffmpeg 自动计算：

MP4（iPhone / Android / macOS）

ffmpeg -i input.mkv \
  -vf "scale=-2:270" \
  -c:v libx264 -profile:v main -level 3.0 -preset fast -crf 28 \
  -c:a aac -b:a 64k -ac 1 \
  -movflags +faststart \
  output.mp4

WebM（Windows 专用）

ffmpeg -i input.mkv \
  -vf "scale=-2:270" \
  -c:v libvpx-vp9 -crf 35 -b:v 0 \
  -c:a libopus -b:a 64k -ac 1 \
  output.webm

scale=-2:270 的含义：

  • 高度固定 270
  • 宽度自动计算，保持宽高比
  • -2 保证宽度是偶数（编码器要求）

270 对 iPhone 和桌面都够用，字幕和口型都能看清。宽度交给 ffmpeg，不用管原始是 16:9 还是 4:3。

7.3 音频压缩

推荐 M4A：

ffmpeg -i input.wav \
  -c:a aac -b:a 64k -ac 1 \
  -movflags +faststart \
  output.m4a

如果必须用 MP3，用 CBR（固定码率）：

ffmpeg -i input.wav \
  -c:a libmp3lame -b:a 64k -ac 1 \
  output.mp3
不要加 -q:a，那会生成 VBR（可变码率）。VBR MP3 除非有 Xing 头，否则 iPhone 上 seek 不准。

7.4 关键参数说明

参数作用
scale=-2:270高度固定 270，宽度自动取偶数
-profile:v mainH.264 主流 profile，iOS 兼容
-level 3.0兼容性保险
-crf 28画质/体积平衡点，再高就糊
-b:a 64k -ac 1音频单声道 64kbps
-movflags +faststartMP4 专有，moov 移到文件开头，iPhone 上能精准 seek 的关键

WebM 不需要 -movflags +faststart，那是 MP4 专有参数。

7.5 如果还是太大

进一步压缩：

  • -crf 32 画质再降一档
  • scale=-2:180 高度降到 180
  • -r 20 帧率降到 20fps
  • -b:a 48k 音频降到 48kbps

7.6 批量转换脚本

Windows 批处理（同一目录下所有 mkv 转 mp4）：

for %%f in (*.mkv) do (
  ffmpeg -i "%%f" -vf "scale=-2:270" ^
    -c:v libx264 -profile:v main -level 3.0 -preset fast -crf 28 ^
    -c:a aac -b:a 64k -ac 1 ^
    -movflags +faststart "%%~nf.mp4"
)

同样目录转 webm：

for %%f in (*.mkv) do (
  ffmpeg -i "%%f" -vf "scale=-2:270" ^
    -c:v libvpx-vp9 -crf 35 -b:v 0 ^
    -c:a libopus -b:a 64k -ac 1 ^
    "%%~nf.webm"
)

8. 媒体必须可精准定位

8.1 什么是"可定位"

定位（seek）指的是播放器跳到文件的任意时间点开始播放。iPhone 上的 AVFoundation 对 seek 的支持取决于容器格式和元数据结构。

如果文件不可定位，会出现：

  • 播放能放，但滑动进度条不准
  • 跳到中间位置会卡住或跳回开头
  • 多个 [sound:] 连续播放时，第二个开始位置错乱
  • 循环播放的起点偏移

8.2 各格式的可定位条件

格式可定位条件不满足时的现象
MP4 / M4Amoov atom 必须在文件开头必须读完整个文件才能 seek，大文件几乎无法定位
WebMiOS AVFoundation 支持不完整iPhone 上无法 seek；Windows 上正常
MP3 (VBR)必须有 Xing/Info 头seek 位置不准
MP3 (CBR)天然可定位—
OGG / OpusiOS 原生不支持完全不能播
AVI / MKV / WMV / FLViOS 原生不支持完全不能播
H.264 + AAC in MP4最稳—

8.3 保证可定位的四条规则

  1. iPhone 上的视频用 MP4（H.264 + AAC），音频用 M4A 或 CBR MP3
  2. -movflags +faststart 让 moov 在开头，否则大文件无法 seek
  3. 视频 profile 不能太新，baseline / main 最稳
  4. 音频采样率统一 44.1kHz 或 48kHz

8.4 检查方法

用 ffprobe 检查 moov 位置：

ffprobe -v trace -i output.mp4 2>&1 | grep -E "type:'moov'|type:'mdat'"

如果先出现 moov 再出现 mdat，说明已经 faststart 处理过。

8.5 一句话总结

iPhone 上的视频转成 H.264 main profile + AAC 的 MP4，必须加 -movflags +faststart；Windows 上的视频转成 VP9/VP8 + Opus/Vorbis 的 WebM。所有音频转成 AAC 的 M4A，或 CBR MP3。

9. 打包成 apkg

9.1 桌面侧准备

  1. 把所有转换好的媒体文件放进 collection.media 文件夹
  2. 打开媒体包 deck（如 MP4 Seinfeld）
  3. 确认 sound 字段里的 [sound:] 引用与实际文件一致
  4. 可以用 Anki 的"检查媒体"确认所有引用都能找到文件

9.2 导出 apkg

  1. 在牌组列表中，右键目标 deck → 导出
  2. 选择"Anki 牌组包（.apkg）"格式
  3. 勾选"包含媒体文件"
  4. 选择保存位置
如果只想导出某个系列或某一季，一定要在导出时选中那个 deck，不要选"所有牌组"。每季单独导出，传输和导入都更稳。

9.3 打包后的验证

  • apkg 文件大小应该接近所有媒体文件的总和
  • 如果 apkg 明显偏小，说明媒体没被打包，检查 [sound:] 引用是否正确
  • 可以用 7-Zip 打开 apkg（本质是 zip），确认里面的 collection.media 有文件

10. 传输到 iPhone

传输的是 apkg 文件本身，不是同步媒体。媒体打包在 apkg 里，一次性传给 iPhone，不经过 AnkiWeb。

10.1 三种方式

方式适用场景优点
iTunes / Finder 文件共享Windows / Mac 用户，首选有线传输，最稳定，无大小限制
网盘无数据线时上传后 iPhone 下载，方便
AirDropMac 用户，中小 apkg无网也可，速度快
U 盘直插大 apkg（> 5GB）不依赖网络，最稳定

10.2 iTunes / Finder 文件共享（首选）

这是最常用的方式，因为它不依赖网络，不受 apkg 大小限制。

Windows（iTunes）

  1. 用数据线连接 iPhone 和电脑
  2. 打开 iTunes，点击设备图标
  3. 进入"文件共享"
  4. 在 App 列表里选择 AnkiMobile
  5. 点击"添加文件"，选择 apkg
  6. iTunes 把 apkg 传到 AnkiMobile 的 Documents 目录
  7. 在 iPhone 上打开 AnkiMobile，apkg 出现在导入列表里

macOS（Finder）

  1. 用数据线连接 iPhone 和 Mac
  2. 打开 Finder，侧边栏点击 iPhone
  3. 进入"文件"标签页
  4. 在 App 列表里选择 AnkiMobile
  5. 把 apkg 拖进文件列表
  6. 在 iPhone 上打开 AnkiMobile 导入

10.3 网盘

常用网盘：iCloud Drive、OneDrive、Google Drive、百度网盘、坚果云。

  1. 电脑上把 apkg 上传到网盘
  2. iPhone 上打开对应网盘 App，下载 apkg
  3. 点击 apkg → 用 AnkiMobile 打开
  4. 或者先存到"文件"App，再点击导入
百度网盘等国内网盘，下载后可能需要先"用其他应用打开"，选择 AnkiMobile。iOS 的文件系统会把它交给 AnkiMobile 处理。

10.4 AirDrop（Mac 用户）

  1. Mac 上右键 apkg → 共享 → 隔空投送
  2. 选择 iPhone
  3. iPhone 上点击"接受"
  4. 系统会提示用哪个 App 打开，选择 AnkiMobile

10.5 U 盘直插（大文件）

  1. 把 apkg 拷到 USB-C 或 Lightning 接口的 U 盘
  2. U 盘插到 iPhone
  3. 打开"文件"App，进入 U 盘
  4. 点击 apkg → 选择用 AnkiMobile 打开

10.6 传输时间参考

apkg 大小iTunes 文件共享网盘AirDrop

11. 导入：先删除旧 deck

这是最容易踩的坑。如果 iPhone 上已经有同名 deck，直接导入 apkg 会失败或被跳过。必须先删除旧的 deck，再导入新的。

11.1 为什么必须先删除

AnkiMobile 在导入 apkg 时，对同名 deck 的处理策略是跳过已存在的笔记，而不是覆盖。这意味着：

  • 同名 deck 已存在 → 新笔记不会导入
  • 已存在的笔记不会被更新
  • 媒体文件也不会被替换

结果就是：你导入了新 apkg，但 iPhone 上还是旧的内容。

11.2 正确的导入流程

  1. 在 AnkiMobile 里找到对应的旧 deck
  2. 长按 deck → 删除（或滑动删除）
  3. 确认删除
  4. 点击 apkg 文件 → 用 AnkiMobile 打开
  5. AnkiMobile 弹出确认框，显示 deck 名和卡片数量
  6. 点击"导入"，等待完成

11.3 删除 deck 会不会影响学习进度

  • 如果这个 deck 是媒体包（只有一张卡片，从不复习），删除无影响
  • 如果是正式学习卡片引用了媒体，删除媒体包 deck 不会影响正式卡片
  • 但删除正式学习 deck 会丢失学习进度，操作前要确认清楚

11.4 批量删除

如果要更新多个季的 deck，可以：

  1. 一次性删除所有要更新的 deck
  2. 再逐个导入新的 apkg

11.5 验证导入成功

  • 打开新导入的 deck，检查卡片数量
  • 查看 media pack 卡片的 sound 字段，确认 [sound:] 都显示为可播放
  • 打开一张正式学习卡片，播放媒体，拖动进度条验证可定位

11.6 导入后的清理

apkg 已经导入 iPhone 后，可以删除传输过程中的 apkg 副本（U 盘里的、网盘里的、iTunes 里的），释放空间。

12. 更新媒体

12.1 什么情况下需要更新

  • 发现某段视频切错了，重新切
  • 压缩参数不对，重新压
  • 字幕时间轴调整，媒体需要重新生成
  • 增加了新的集数

12.2 更新流程

  1. 桌面侧生成新的媒体文件
  2. 保持文件名不变，覆盖 collection.media 里的旧文件
  3. 确认 sound 字段里的引用不需要改（如果文件名没变）
  4. 重新导出 apkg，勾选"包含媒体文件"
  5. 传到 iPhone
  6. 先在 iPhone 上删除对应的旧 deck
  7. 再导入新的 apkg
媒体不走同步，更新只能通过"删除旧 deck → 重新导入 apkg"完成。不存在"只同步一个文件"这种操作。

12.3 增加新媒体

  1. 新文件按命名规范命名，如 sf_s02e13.mp4
  2. 放进 collection.media
  3. 在 sound 字段末尾追加一行 [sound:sf_s02e13.mp4]
  4. 重新导出 apkg
  5. 删除 iPhone 上的旧 deck
  6. 导入新的 apkg

12.4 改文件名

改文件名是高风险操作，因为旧文件会残留在 iPhone 上。除非必要，不要改文件名。要改的话：
1. 新文件名按规范命名
2. 卡片引用同步改
3. 重新导出 apkg
4. 删除旧 deck 再导入
5. 旧文件用第 13 节的方法清理

13. 删除指定媒体文件

这一节的技巧是整份说明书的核心：通过删除 [sound:] 引用，触发 Anki 的"检查媒体"来清理 iPhone 上的媒体文件。

13.1 原理

Anki 的"检查媒体"会扫描整个媒体库，找出没有被任何卡片引用的文件，列在"未使用文件"里，允许用户删除。

因此，只要：

  1. 从卡片字段里删掉对应的 [sound:xxx.mp4]
  2. 重新导出 apkg 并导入 iPhone（记得先删除旧 deck）
  3. 在 AnkiMobile 里运行"检查媒体"
  4. 该文件就会出现在"未使用文件"列表里，可以删除

13.2 完整操作步骤

步骤 1：删除 sound 字段里的引用

在桌面 Anki 里，打开媒体包 deck 的卡片，从 sound 字段里删掉要清理的 [sound:xxx.mp4] 行。

步骤 2：确认引用已经被清掉

用 Anki 的搜索功能，在整个收藏里搜索 xxx.mp4，确认没有其他卡片还在引用这个文件。

在 Anki 搜索框输入：xxx.mp4

如果还有结果，说明其他卡片还在用，不能删。

步骤 3：重新导出 apkg

把媒体包 deck 重新导出 apkg。此时因为 sound 字段里已经没有该引用，Anki 打包时不会包含该文件。

步骤 4：传到 iPhone

通过 iTunes 文件共享 / 网盘 / AirDrop / U 盘传到 iPhone。

步骤 5：先删除 iPhone 上的旧 deck

在 AnkiMobile 里找到对应的旧 deck，删除。

步骤 6：导入新的 apkg

点击新的 apkg，用 AnkiMobile 导入。

步骤 7：运行"检查媒体"

在 AnkiMobile 里（或桌面 Anki 里）运行"检查媒体"。该文件现在没有任何引用，会出现在"未使用文件"列表里。

步骤 8：删除未使用文件

确认后删除。空间释放。

13.3 为什么这个流程有效

AnkiMobile 的"检查媒体"会扫描本地媒体库，对照卡片引用，找出孤儿文件。只要文件不再被引用，无论它是大是小，都会被列为"未使用"。

13.4 注意事项

  • 前提是该文件小于 100MB。超过 100MB 的文件不参与"未使用"判定，见第 14 节
  • 删除引用后，卡片上播放这段媒体会显示"媒体缺失"，这是预期的
  • 如果不想让卡片显示缺失提示，应该同时删掉卡片，或把卡片也一起清理
  • 操作前备份 apkg，以防误删
  • 如果 iPhone 上的"检查媒体"没有找到该文件，可能是导入没成功，重新导入一次

13.5 批量删除多个媒体

如果要清理多个文件，一次性从 sound 字段里删掉所有对应的 [sound:] 行，然后重新导出 apkg。导入后运行一次"检查媒体"就能全部清理。

14. 清理超过 100MB 的大文件

14.1 问题描述

如果媒体文件超过 100MB，即使用户已经删掉了引用它的卡片，文件仍然会留在媒体库里，无法通过"检查媒体 → 删除未使用文件"清除。

14.2 根本原因

Anki 的"检查媒体"对超过 100MB 的文件有特殊处理：

  • 它们被单独归入"超过 100MB 的文件"列表
  • 不参与"未使用文件"的判定
  • 所以无论卡片是否还引用它，都无法通过内置功能删除

这个设计的根源是 AnkiWeb 对单个媒体文件有 100MB 的同步上限。Anki 假设这类文件需要用户手动处理。

14.3 解决思路

用一个同名的小文件覆盖掉大文件，让它降到 100MB 以下。此时 Anki 会把它当作普通文件处理，如果卡片已经不再引用它，就会被正常列为"未使用文件"，可以删除。

14.4 完整操作步骤

步骤 1：删掉卡片引用

在桌面 Anki 里，去掉卡片字段中对该媒体的 [sound:xxx.mp4] 引用，或者直接删掉整张卡片。

步骤 2：准备同名小文件

创建一个与原文件同名的小文件，大小远小于 100MB。

Windows：

type nul > xxx.mp4

或者用 ffmpeg 生成 1 秒静音片段：

ffmpeg -f lavfi -i anullsrc=r=44100:cl=mono -t 1 -c:a aac -movflags +faststart xxx.mp4

步骤 3：覆盖 collection.media 里的原文件

打开桌面 Anki 的媒体文件夹（工具 → 检查媒体 → 查看文件），把刚准备的小文件复制进去，覆盖原大文件。

步骤 4：重新导出 apkg

把这个系列（或这个媒体包 deck）重新导出 apkg，勾选"包含媒体文件"。

步骤 5：传到 iPhone 重新导入

通过 iTunes 文件共享 / 网盘传到 iPhone。

先在 iPhone 上删除对应的旧 deck，然后用 AnkiMobile 导入新的 apkg。同名小文件会覆盖手机上的大文件。

步骤 6：运行检查媒体

此时这个文件已经小于 100MB，会出现在"未使用文件"列表里。删除它，空间释放。

14.5 为什么同名覆盖有效

Anki 的媒体库是按文件名管理的。用同名文件覆盖后，Anki 在导入 apkg 时发现同名文件已存在，会用新文件替换旧文件。这样旧的大文件就被替换掉了。

14.6 前提条件

  • 卡片必须先不再引用该文件，否则即使文件变小了，Anki 仍认为它是"使用中"，不会删除
  • 覆盖操作要在桌面完成，因为 iPhone 端无法直接访问 AnkiMobile 的媒体文件夹
  • 如果 iPhone 上的文件没被替换，可能是导入没成功，重新导入一次

14.7 注意事项

  • 如果这个文件还有其他卡片在引用，覆盖后播放效果会变（变成静音或极小片段）。确保所有引用都已清掉再覆盖
  • 覆盖前备份 collection.media，以防误操作
  • 这个方法是清理超过 100MB 大文件的唯一途径

14.8 更好的做法：从源头避免

最省事的做法是从一开始就把每个媒体文件压到 100MB 以下。用第 7 节的 ffmpeg 参数，30 分钟一集通常能压到 30-50MB。这样永远不会遇到 100MB 问题，清理时直接用第 13 节的方法即可。

  1. 从 sound 字段删掉对应的 [sound:] 行

16. 常见问题

Q1：导入 apkg 后，deck 里还是旧内容
因为 iPhone 上已存在同名 deck，AnkiMobile 跳过了导入。先在 iPhone 上删除旧 deck，再导入。
Q2：apkg 导出后体积很小，媒体没被包含
检查 [sound:] 引用的文件名是否和实际文件名完全一致（包括扩展名和大小写）。Anki 只打包能被卡片引用的媒体。
Q3：Windows 上视频播不了
Windows 版 Anki 只支持 WebM。用 ffmpeg 把 MP4 转成 WebM： 
ffmpeg -i input.mp4 -vf "scale=-2:270" -c:v libvpx-vp9 -crf 35 -b:v 0 -c:a libopus -b:a 64k -ac 1 output.webm
Q4：iPhone 上媒体播放正常，但进度条乱跳
文件不是"可定位"的。用 ffmpeg 重新转，必须加 -movflags +faststart，视频用 main profile，音频用 CBR MP3 或 M4A。
Q5：删了 [sound:] 引用，但检查媒体找不到该文件
可能原因：
1. 还有其他卡片在引用该文件。用 Anki 搜索功能搜文件名确认
2. 重新导入 apkg 时没成功
3. 该文件大于 100MB，不参与"未使用"判定，需要用第 14 节的方法
Q6：删了卡片，但媒体文件还在占空间
删卡片不会自动删媒体。需要在 sound 字段里也删掉引用，然后重新导入并运行检查媒体。
Q7：超过 100MB 的文件，检查媒体里找不到
这是 Anki 的设计：超过 100MB 的文件被单独归类，不参与"未使用"判定。用同名小文件覆盖法处理（第 14 节）。
Q8：能不能用 AnkiWeb 同步媒体？
不能。原因：
1. 几十 G 的流量不可能
2. 单文件超过 100MB 无法同步
3. AnkiWeb 免费账户有容量限制
所以媒体只能通过 apkg 离线传输。
Q9：正式卡片的引用和媒体包的 [sound:] 会不会冲突
不会。媒体包只是一个"传输载体"，正式卡片的引用指向同一批文件。文件在 iPhone 上就位后，正式卡片就能找到。
Q10：文件名大小写在 Windows 和 iPhone 上不一致
Windows 文件系统不区分大小写，iOS 区分。为避免问题：
1. 文件名全小写
2. [sound:] 引用也用全小写
3. 不要在 Windows 上命名成 File.mp4，再在引用里写成 file.mp4
Q11：媒体包 deck 里的卡片会不会在复习时出现
如果媒体包 deck 有学习计划，可能会出现。处理方法：
1. 把媒体包 deck 的学习选项设为"暂停"
2. 或者把媒体包 deck 从复习计划中排除
3. 或者把媒体包 deck 里的卡片设置成"已暂停"
Q12：ffmpeg 转换后视频变糊了
调整参数：
1. -crf 降低（如 24），画质提升，体积增大
2. scale=-2:360 高度提到 360，分辨率提升
3. -preset 改为 slow，编码更精细
语言学习场景下，只要字幕能看清就够了。
Q13：多个季一起打包成一个 apkg 可以吗
可以，但建议分开。原因：
1. 单个 apkg 太大会导致传输慢、导入慢
2. 更新某一季时要重新传整个大包
3. 清理时粒度太粗
每季一个 apkg 最灵活。
Q14：能不能不用 apkg，直接拷文件到 iPhone
不能。iOS 沙盒机制下，AnkiMobile 的 collection.media 不暴露在文件 App 里。唯一可靠的传输方式是 apkg。
Q15：iTunes 文件共享里看不到 AnkiMobile
确认：
1. iPhone 上已安装 AnkiMobile
2. iPhone 已解锁并信任此电脑
3. iTunes 已识别到设备
4. AnkiMobile 开启了文件共享（AnkiMobile 默认开启）
Q16：为什么每次更新都要删 deck 再导入
这是 AnkiMobile 的导入策略。AnkiWeb 的同步是增量的（按修改时间比较），但 apkg 导入不是增量，而是"批量添加"。同名笔记被跳过，所以只能先删除再导入。
Q17：网盘下载的 apkg 用 AnkiMobile 打不开
可能原因：
1. 网盘 App 没提供"用其他应用打开"的选项，先存到"文件"App 再点击
2. apkg 下载不完整，重新下载
3. AnkiMobile 版本太旧，升级到最新版
Q18：转视频时一定要指定宽度吗
不需要。用 scale=-2:270，高度固定 270，宽度自动计算，保持宽高比。-2 保证宽度是偶数。这样不管原始视频是 16:9、4:3 还是其他比例，ffmpeg 都会自动算出合适的宽度。
